# Development

## Stack

| Part | Technology |
|---|---|
| Backend | Python 3.14, FastAPI, httpx (async Vault client), `cryptography` |
| Frontend | React 19, TypeScript, Vite. No UI library; plain CSS with light and dark themes |
| Image | One container: FastAPI serves the built UI. Multi-stage build on Red Hat Hardened Images |
| Local stack | Podman (or Docker) Compose: two Vaults, Dex, seed job, the app; optional k3s, test and docs profiles |

```
backend/src/lockstep/
  api/          connections · compare (+ history) · sync · analyze · auth (OIDC)
  analyze/      content detection, certificates and chains, DER reader, JKS/JCEKS reader
  cli/          the `lockstep` command: compare -> YAML report, apply (connect, report, apply)
  engine.py     comparing two locations (shared by the API and the CLI)
  diff.py       pure comparison logic        vault.py    Vault HTTP client
  session.py    encrypted cookie sessions    config.py   LOCKSTEP_* settings
backend/tests/  pytest, run against the compose Vaults
frontend/src/   App, components/ (SideCard, Results, SecretRow, ReviewDialog, Inspector, CertCard…)
dev/            dex/, seed/ (demo data, real keytool keystores), k8s/ (k3s setup, chart test), e2e/ (browser tests, screenshots)
charts/lockstep Helm chart (values.schema.json, ci/ value sets for checks)
scan/ scripts/  security scanning, image pin maintenance
docs/           these guides; docs/images is generated by `make screenshots`
```

## Make targets

| Target | Does |
|---|---|
| `make up` | Build and start the stack: Vault A and B, Dex, seed, app on http://localhost:8080 |
| `make up-k8s` | Also start k3s and set up Kubernetes auth (see [authentication](authentication.md#trying-it-locally)) |
| `make down` | Stop everything (all profiles) |
| `make test` | Backend tests against the seeded Vaults |
| `make test-k8s` | Tests including real Kubernetes logins through k3s |
| `make chart-check` | Helm chart: lint, Kubernetes schema validation of the rendered objects, guard checks (no cluster) |
| `make helm-test` | Install the chart into the dev k3s cluster and test it for real (needs `make up-k8s`) |
| `make e2e` | Browser end-to-end tests (Playwright) → `reports/e2e` (JUnit, screenshots of failures) |
| `make screenshots` | Regenerate `docs/images/*` (dark and light) by driving the app with Playwright |
| `make scan` | Security scan to `reports/`; fails on the gate |
| `make bump-base-images` | Update the Red Hat base image digests to the latest builds |
| `make pin-scanner-images` | Re-pin scanner images to multi-arch digests |

## Demo environment

| Service | URL | Credentials |
|---|---|---|
| Tool | http://localhost:8080 | — |
| Vault A | http://localhost:8200 | root token `root-a` |
| Vault B | http://localhost:8201 | root token `root-b` |
| Dex (OIDC) | http://dex.localhost:5556/dex | `alice@example.com` / `password`, `bob@example.com` / `password` |

The Vaults run in dev mode (in memory). The **seed job recreates its mounts on every run** (each `make up`, and before every test run), so the demo data always starts from the same state, however much you've copied or edited by hand.

**Users** (on both Vaults, password `password`):

| Sign-in | Policy | Access |
|---|---|---|
| userpass `alice`, OIDC `alice@example.com` | `lockstep-admin` | everything (via an identity entity for OIDC) |
| userpass `bob`, OIDC `bob@example.com` | `lockstep-readonly` | read and list every KV mount, plus `sys/mounts` |
| userpass `carol` | `lockstep-limited` | `app-config` only, no `sys/mounts`. `restricted/` is hidden; `payments/api` can be listed but not read |
| Kubernetes (with `make up-k8s`) | per role | see [authentication](authentication.md#trying-it-locally) |

**Mounts:**

| Mount | Where | Contents |
|---|---|---|
| `app-config` | A and B | equal, different and one-sided secrets and keys; deep nesting; a path with a space; JSON values with a number vs a string; a soft-deleted secret; base64 text; PNG and SVG (with a `<script>` that must not run); a JAR; random AES/HMAC keys |
| `certs` | A and B | root and intermediate CA; valid, renewed (differs A vs B), expired, not-yet-valid, self-signed, untrusted and missing-intermediate leaves; DER in base64; a base64 PEM chain; PKCS#12 with and without a password; **JKS and JCEKS keystores made by `keytool`** (password `changeit`) |
| `team-a-only` | A | one-sided mount |
| `app-config-staging` | B | for comparing two mounts in the same Vault |
| `legacy-kv` | A and B | KV v1; must be ignored |

## Tests

```sh
make test        # or: podman compose --profile test run --rm --build tests
```

The tests run in a container on the compose network, against the seeded Vaults and Dex. They cover the diff engine, sessions, connections and permissions, copying (CAS, conflicts, audit), last-changed history, value detection (certificates, PKCS#12, JKS/JCEKS, images…), the OIDC login through Dex, the command line (reports, action checks, compare and apply against both Vaults), and Kubernetes auth (with real k3s logins when the token is mounted; otherwise those tests are skipped). Tests that write data use a random prefix and remove it afterwards.

For the UI with hot reload:

```sh
cd frontend && npm install && npm run dev     # http://localhost:5173, proxies /api to :8080
```

`npm run build` typechecks (strict TypeScript) and builds.

To try the CLI against the local stack (Vault A on :8200 with token `root-a`, Vault B on :8201 with `root-b`):

```sh
python3 -m venv .venv && .venv/bin/pip install -e backend
VAULT_TOKEN=root-a LOCKSTEP_RIGHT_TOKEN=root-b .venv/bin/lockstep compare \
  --left-addr http://localhost:8200 --right-addr http://localhost:8201 --mount app-config -o report.yaml
```

## Browser end-to-end tests

```sh
make e2e
```

`dev/e2e/tests` drives the real UI in Chromium (Playwright) against the running stack. It covers the main user journeys:

| Test | Checks |
|---|---|
| sign in, compare, filter | userpass sign-in on both sides through the form; statuses; status filters; search |
| values masked until revealed | values absent from the page until *Show values*, and gone again after |
| type difference and last changed | `number` vs `string` tags; per-key "changed … · vN" |
| copy with review, conflict and audit | staging two copies; the review; a concurrent edit in Vault B; one written, one **conflict**; target values checked in Vault |
| OIDC redirect login | the full round trip through Dex's login page and back |
| limited user | the mount-list fallback notice; folders hidden by policy shown as **No access** |
| inspect PKCS#12 | both sides; sibling password key; certificate diff; chain becomes trusted after picking `ca/root` |
| SVG preview | the image renders and its `<script>` does not run |
| Kubernetes sign-in | with `make up-k8s` only (otherwise skipped) |

The browser reaches the app as `http://localhost:8080` and Dex as `http://dex.localhost:5556`, the same URLs as locally. Chromium host rules map them to the compose services, so the OIDC callback works unchanged. Tests that write data use a random prefix and remove it afterwards.

## Screenshots

`make screenshots` re-seeds the demo data, then runs `dev/e2e/screenshots.py` (Playwright, Chromium) against the running app. It writes every scene in dark and light to `docs/images/`. The README picks the variant that matches the reader's theme. Run it after UI changes and commit the images.

## Base images

The app, the seed job and Dex use **Red Hat Hardened Images** (`registry.access.redhat.com/hi/*`): distroless runtime images (user 65532, no shell, no package manager) with `*-builder` variants for build stages. The Dockerfile therefore uses exec-form `RUN`/`HEALTHCHECK`/`ENTRYPOINT` in the final stage.

Every image is pinned by digest. Red Hat rebuilds these images with security fixes almost daily:

```sh
make bump-base-images && make scan
```

Digests are always resolved **from the registries** as multi-arch indexes (amd64 + arm64), never from a local `podman inspect`. On an Apple-silicon Mac that can return an arm64-only manifest, which breaks amd64 CI runners. The scan checks this.

Vault has no hardened image (neither does OpenBao). It only runs in the demo stack; in real use the tool talks to your Vaults.

## Security scanning

```sh
make scan        # writes reports/ (gitignored); exits non-zero if the gate fails
```

| Step | Tool | Fails the gate on |
|---|---|---|
| Image pins | `scripts/pin-scanner-images.py --check` | any pin that isn't a multi-arch index |
| Base image signatures | cosign + Red Hat's key | any Red Hat image that fails verification |
| Image: OS and language packages | **Grype** | HIGH/CRITICAL with a fix available; the OS not being detected |
| Image: language packages | Trivy | HIGH/CRITICAL with a fix available |
| Repo files (lockfiles, Dockerfiles) | Trivy | fixable HIGH/CRITICAL CVEs; HIGH/CRITICAL misconfigurations |
| Helm chart, rendered with minimal and all-options values | Trivy config | HIGH/CRITICAL Kubernetes misconfigurations. Scanned explicitly, because Trivy renders charts with default values, which this chart rejects, and then silently skips them |
| `dev/` tooling (seed, e2e, k8s) | Trivy config | HIGH/CRITICAL misconfigurations. Scanned separately, because Trivy skips any directory named `dev` by default |
| Python dependencies | pip-audit | any vulnerability with a fix |
| npm dependencies | npm audit | HIGH/CRITICAL in production dependencies with a fix |
| Python source | bandit | HIGH severity at medium or higher confidence |
| Git history | gitleaks | any finding |

Grype is the main image scanner, because Trivy doesn't yet recognise the Hummingbird OS used by Red Hat Hardened Images (Trivy discussion #11180) and silently skips its OS packages. `reports/summary.md` lists every finding with its severity and fixed version; JSON and SARIF reports sit alongside it.

**Allowlists:** prefer `make bump-base-images` over adding entries.
- `.grype.yaml`: each `reason` must end `until YYYY-MM-DD`, and the gate fails after that date. Package names are regexes, so escape `+`.
- `.trivyignore.yaml`: each entry needs a statement and an expiry.
- `scan/pip-audit-ignore.txt`, `.gitleaks.toml` (exact values only), `[tool.bandit]` in `backend/pyproject.toml`.

## CI

Two workflows run on every pull request and on `main`, on GitHub Actions (`.github/workflows`) and on Gitea Actions (`.gitea/workflows`, same steps):

| Workflow | Does | Artifact |
|---|---|---|
| `security.yml` | `scripts/scan.sh` and `scripts/chart-check.sh`, with the binaries copied out of the same digest-pinned images used locally | `security-reports` (summary, JSON, SARIF); on GitHub the SARIF also goes to code scanning |
| `e2e.yml` | Starts the whole demo stack and runs the browser tests | `e2e-reports` (JUnit, failure screenshots, app and seed logs) |

The e2e job runs the stack as its own compose project (`lockstep-ci-<run>`) with `compose.ci.yaml`, which publishes **no ports**, so runs can't clash with each other or with other services on the CI host. Nothing is bind-mounted (Dex's config and the tests are baked into images), because a runner's Docker host can't see the job's checkout. The stack is removed, volumes included, at the end of every run.

## Releasing

1. Set the new version in `charts/lockstep/Chart.yaml` (`version`, `appVersion` and the image in the `artifacthub.io/images` annotation), `backend/pyproject.toml` and `frontend/package.json`, and add a `## [X.Y.Z]` section to `CHANGELOG.md`. Rewrite the chart's `artifacthub.io/changes` annotation for the release (Artifact Hub shows it). `scripts/check-version.sh vX.Y.Z` checks the versions agree.
2. Merge, publish to GitHub (`scripts/publish-github.sh …`), then tag the published commit `vX.Y.Z` on GitHub.
3. `.github/workflows/release.yml` re-runs the security gate and browser tests, builds the amd64 and arm64 image, pushes it to `ghcr.io/<owner>/lockstep` with an SBOM and provenance, pushes the chart to `oci://ghcr.io/<owner>/charts/lockstep`, signs both with cosign (keyless), and creates the GitHub Release from the changelog. A tag like `v0.2.0-rc.1` makes a pre-release (no `latest` tag).

### Artifact Hub

The chart is listed on [Artifact Hub](https://artifacthub.io) from its OCI repository, `oci://ghcr.io/welshstew/charts/lockstep`. Its page there comes from `Chart.yaml`:
- **Annotations:** category, links, image, and the changes in this version.
- **The chart README.**
- **The values schema.**

The "Verified Publisher" badge needs `charts/lockstep/artifacthub-repo.yml` to hold the repository ID Artifact Hub assigns. Once it does, `.github/workflows/artifacthub.yml` pushes the file as `ghcr.io/welshstew/charts/lockstep:artifacthub.io`. That happens on merge, or when you run the workflow manually. `.helmignore` keeps the file out of the chart package.

## The website

getlockstep.cloud is the static landing page in `deploy/demo/site`. Its docs and guide pages are generated from `docs/*.md` and `docs/guides/*.md`, and so is `sitemap.xml`. `scripts/build-site.sh` generates them, using Python-Markdown in `.venv-site/`, and `scripts/deploy-demo.sh` runs it before copying the site to the server. The generated files are gitignored.
- **Which pages:** `DOCS` in `scripts/build_site.py` lists the reference guides that are published. Every guide in `docs/guides/` is published.
- **Links:** links between published pages become site links, and links to anything else in the repository go to GitHub. Keep links relative (`../cli.md#install`) so they work on GitHub too.
