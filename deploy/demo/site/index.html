Keep your Vault clusters in lockstep.

Compare, inspect and sync KV v2 secrets across HashiCorp Vault clusters, environments and mounts. Values are compared on the server, so nothing is shown unless you ask for it.

Everything you need to keep secrets in sync

Compare anything to anything

Two Vaults, two mounts or two path prefixes. See which secrets and keys are equal, different, or only on one side, down to a 5432 vs "5432" type change.

Values stay hidden

The browser only gets a status per key. Show values reveals them for the secrets you open, and nothing else.

Copies you can trust

Copy a key or a whole secret with ← / → after a review. Check-and-set writes never overwrite a change made since you compared. Nothing is deleted, and every write is audit-logged.

Sync plans

Save reviewed changes as a signed file, with no values in it, for someone with write access to apply. If anything in it has changed since, nothing is written.

Certificates and keystores

Base64, PEM, X.509 chains validated link by link, PKCS#12, JKS and JCEKS. Inspect them, compare them field by field, and see every certificate's expiry on one dashboard.

Comparison profiles

Pair services/*/prod/** with services/*/staging/**, ignore keys that differ by design, and share the rules with your team.

Review before anything is written

Stage copies key by key. The review shows exactly what each target will get, its version change, and whether you're allowed to write it. Then apply it yourself, or save it as a plan for someone else.

Know what each value is

Lockstep works out what's inside each value: a PKCS#12 file, a Java keystore, a certificate chain, an image. It opens keystores with the password stored next to them and checks every certificate.

See what expires when

Every certificate in one or both mounts, including those inside keystores, sorted by expiry. Filter, inspect, and export to CSV.

From the terminal, too

lockstep compare writes a YAML report of what differs: no values, but a Vault UI link and a vault kv get command for every secret. Set an action on the keys to change and lockstep apply copies them, asking before each one. It logs in like the vault CLI, and its exit code makes it a drift check in CI.

$ lockstep compare --mount app-config -o report.yaml
  different   payments/db     differs: password
  left only   services/api
  right only  services/queue

12 secrets: 9 equal, 1 different, 1 left only, 1 right only.

$ lockstep apply report.yaml
→ staging · app-config/payments/db   from prod · app-config/payments/db
  1 key to write (v7 → v8):
    update password
  Write password? [y]es / [n]o / [a]ll / [q]uit: y
  Written: v8 (1 key).

Built to run in production

  • Stateless. Sessions live in an encrypted cookie, so any number of replicas can serve any request.
  • Sign in your way. Token, userpass, LDAP, OIDC redirect, or the pod's Kubernetes service account.
  • Hardened images. Distroless and non-root on Red Hat Hardened Images, multi-arch, signed with cosign, with an SBOM and build provenance.
  • A Helm chart that's tested. Read-only filesystem, NetworkPolicy, PodDisruptionBudget, a session key kept across upgrades, all installed into a real cluster in CI.
  • Scanned on every change. CVEs, leaked secrets, misconfigurations and base image signatures, plus end-to-end browser tests.
  • Configured by environment. Everything is a LOCKSTEP_* variable or a chart value.

Install

Kubernetes (Helm)

helm upgrade --install lockstep \
  oci://ghcr.io/welshstew/charts/lockstep \
  -n lockstep --create-namespace \
  --set 'vaults[0].name=Production' \
  --set 'vaults[0].url=https://vault.example.com'

Try it locally

git clone https://github.com/welshstew/lockstep
cd lockstep
make up    # two demo Vaults + Lockstep
open http://localhost:8080

Command line

pipx install "git+https://github.com/welshstew/lockstep@v0.2.0#subdirectory=backend"
lockstep compare --help

# or run it from the image
docker run --rm -it --entrypoint lockstep ghcr.io/welshstew/lockstep:0.2.0 --help

Configuration, authentication, deployment and command-line guides are in the documentation.
