Keep your Vault clusters in lockstep.

Compare, inspect, sync and migrate KV v2 secrets across HashiCorp Vault clusters, environments and mounts. Values are compared on the server, so nothing is shown unless you ask for it.

Everything you need to keep secrets in sync

Compare anything to anything

Two Vaults, two mounts or two path prefixes. See which secrets and keys are equal, different, or only on one side, down to a 5432 vs "5432" type change.

Values stay hidden

The browser only gets a status per key. Show values reveals them for the secrets you open, and nothing else.

Copies you can trust

Copy a key or a whole secret with ← / → after a review. Check-and-set writes never overwrite a change made since you compared. Nothing is deleted, and every write is audit-logged.

Sync plans

Save reviewed changes as a signed file, with no values in it, for someone with write access to apply. If anything in it has changed since, nothing is written.

Certificates and keystores

Base64, PEM, X.509 chains validated link by link, PKCS#12, JKS and JCEKS. Inspect them, compare them field by field, and see every certificate's expiry on one dashboard.

Comparison profiles

Pair services/*/prod/** with services/*/staging/** and ignore keys that differ by design. Build the rules by clicking Ignore in the results, then share them with your team.

Export, import and migrate

Export a mount to an encrypted file, compare a Vault against it, or import it elsewhere with rules: leave paths and keys out, and turn dev into test on the way.

Set values yourself

Override left, right or both with values you type, text or JSON, through the same review and check-and-set write as a copy. Typed values are never stored or logged.

Finds keystore passwords

A certs.p12 in one folder, its password in strings/KEYSTORE_PASSWORD in another: Lockstep tries the likely candidates on the server and offers the one that opens it, without showing a value.

Review before anything is written

Stage copies key by key. The review shows exactly what each target will get, its version change, and whether you're allowed to write it. Then apply it yourself, or save it as a plan for someone else.

Promote a whole environment

Export production's services/ with a one-time key, then import it into staging: paths /prod/ become /staging/, values ending -prod end -staging. The preview shows every secret and key before anything is written, and keys only on the target are kept.

Ignore the noise in a few clicks

Hostnames and per-environment passwords are meant to differ. Press Pick what to ignore…, click Ignore on the secrets, folders and keys that don't matter, check the result, and save it as a profile for the next comparison and for CI.

Guide: build a comparison profile →

Know what each value is

Lockstep works out what's inside each value: a PKCS#12 file, a Java keystore, a certificate chain, an image. It opens keystores with the password stored next to them, or finds it elsewhere in the folder, and checks every certificate.

See what expires when

Every certificate in one or both mounts, including those inside keystores, sorted by expiry. Filter, inspect, and export to CSV.

From the terminal, too

lockstep compare writes a YAML report of what differs: no values, but a Vault UI link and a vault kv get command for every secret. Set an action on the keys to change and lockstep apply copies them, asking before each one. It logs in like the vault CLI, and its exit code makes it a drift check in CI.

$ lockstep compare --mount app-config -o report.yaml
  different   payments/db     differs: password
  left only   services/api
  right only  services/queue

12 secrets: 9 equal, 1 different, 1 left only, 1 right only.

$ lockstep apply report.yaml
→ staging · app-config/payments/db   from prod · app-config/payments/db
  1 key to write (v7 → v8):
    update password
  Write password? [y]es / [n]o / [a]ll / [q]uit: y
  Written: v8 (1 key).

Built to run in production

  • Stateless. Sessions live in an encrypted cookie, so any number of replicas can serve any request.
  • Sign in your way. Token, userpass, LDAP, OIDC redirect, JWT (a CI job's identity token), or the pod's Kubernetes service account.
  • Hardened images. Distroless and non-root on Red Hat Hardened Images, multi-arch, signed with cosign, with an SBOM and build provenance.
  • A Helm chart that's tested. Read-only filesystem, NetworkPolicy, PodDisruptionBudget, a session key kept across upgrades, all installed into a real cluster in CI.
  • Scanned on every change. CVEs, leaked secrets, misconfigurations and base image signatures, plus end-to-end browser tests.
  • Configured by environment. Everything is a LOCKSTEP_* variable or a chart value, including whether exports are allowed, encrypted-only or off.

Install

Kubernetes (Helm)

helm upgrade --install lockstep \
  oci://ghcr.io/welshstew/charts/lockstep \
  -n lockstep --create-namespace \
  --set 'vaults[0].name=Production' \
  --set 'vaults[0].url=https://vault.example.com'

Try it locally

git clone https://github.com/welshstew/lockstep
cd lockstep
make up    # two demo Vaults + Lockstep
open http://localhost:8080

Command line

pipx install "git+https://github.com/welshstew/lockstep@v0.3.0#subdirectory=backend"
lockstep compare --help
lockstep export --help    # and lockstep import

# or run it from the image
docker run --rm -it --entrypoint lockstep ghcr.io/welshstew/lockstep:0.3.0 --help

Configuration, authentication, deployment and command-line guides are in the documentation.

Guides

How to compare secrets between two Vault clusters

Diffing with the vault CLI and where it falls short, then comparing whole mounts in the browser or from the terminal.

Syncing secrets between environments safely

Check-and-set writes, merges without deletes, reviews, and sync plans for changes someone else applies.

Detecting secret drift in CI

Fail a pipeline when two Vault environments drift apart, with a read-only token and no values in the logs.

Exporting, importing and migrating Vault secrets

Encrypted exports, comparing a Vault against a backup, and promoting dev to test with import rules.

Building a comparison profile

Pick what to ignore in the results, map paths between layouts, and reuse the profile in the UI and in CI.

Logging in with JWT from CI

Use a pipeline's OIDC identity token with Vault's JWT auth method: no stored secrets, short-lived tokens.
